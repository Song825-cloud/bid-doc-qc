# 问题清单版报告规范（固定约定）

> 这是固化的对外交付口径。**任何项目都按这套出**，不要临场改。

## 一、为什么用「问题清单」而不是「逐项明细」

一次典型质检中，检查项往往有几十上百条，但按问题归并后只有二三十个真正的缺陷——
同一问题最多被拆成多条呈现（例如同一处表述错误出现在多个章节＝多条）。

直接后果：用户要改的是二三十件事，报告却让他读上百条，且同一信息在
速览表 / 明细表 / 整改清单三处重复出现。**问题清单版只保留需整改项。**

## 二、四条铁律

1. **一问题一记**：同一问题只出现一次，全部出现位置并入同一行的「出现位置」列
2. **通过项不进正文**：「已核查且合规」与「待补充材料」全部下沉附录
3. **删掉速览表**：它与整改清单重复度极高，是纯冗余
4. **按问题组织，不按审查视角组织**：第一/二/三/四重/专项是内部核查视角，
   视角切分正是跨表重复的根源；对外只输出问题分类

## 三、问题清单固定 7 列

| 列 | 内容 |
|---|---|
| 编号 | 1—N 纯数字 |
| 问题 | 正常查找口径直述：什么错、错在哪、应该是什么 |
| 等级 | P0 / P1 / P2 |
| 原条目 | 完整版报告中的原编号（可追溯） |
| 出现位置（投标页码） | 合并去重，超过 6 个显示「等N处」 |
| 招标依据页码 | 带来源前缀，如「正文 Pxxx」「答疑 Pxx」 |
| 处理建议 | 具体怎么改 |

**明确不列**：责任人、完成时限、状态、复核人（分工管理列不需要）。

## 四、表述规范

**用正常查找口径**，不要抽象管理术语：

| 不要这样写 | 要这样写 |
|---|---|
| 他标段名称误写进本标段（模板未改干净） | 承诺函、项目名称等处误写为其他标段名称；用电负荷、供风站、水保表土剥离、框格梁护坡、场内交通取电等部位也写成他标段名称，均应改成本标段实际名称 |
| 关键节点日期多个口径并存 | 某关键节点日期三个写法不一致：写法一、写法二、写法三（照抄原文） |
| 浇筑时点与自述沉降期无法同时成立 | 某部位浇筑安排在 X 月，同时又写须沉降 N 个月，而到顶至浇筑仅 M 个月；另处又称须沉降 K 个月，三个条件无法同时成立 |
| 压实设备缺配置（全文 0 命中） | 压实设备未配置：「平仓机」「光面碾」「羊脚碾」全文未出现，缺少型号、台数与压实遍数 |

**禁用词**：根因、闭环、抓手、顶层设计、对齐、颗粒度。
（`check_slim.py` 会把「根因 / 责任人 / 复核人」列为断言，出现即失败。）

## 五、等级定义

| 等级 | 含义 | 时限 |
|---|---|---|
| P0 致命 | 可能造成否决投标，或评委一眼可见、必然扣分 | 投标截止前必须改完 |
| P1 严重 | 影响评分点判定，或造成「前后不一致」的扣分判断 | 投标截止前改完 |
| P2 一般 | 规范性、格式性问题，不影响实质评审 | 建议改完 |

同一问题在多个维度出现时**只计一次**，取最贴切的维度计级。

## 六、报告结构（8 张表）

| 表 | 内容 |
|---|---|
| 1 | 等级图例与统计 |
| 2 | **问题清单** |
| 3 | 关键招标基准（全文核查锚点） |
| 4 | 技术评分点响应与失分风险（含「对应问题编号」列） |
| 5 | 专项核查关键取证（含原文数值与页码） |
| 6 | 报送前形式要件自查 |
| 附录一 | 已核查且合规 |
| 附录二 | 待补充材料 |

附录三：页码定位方法与口径说明（文字）。
