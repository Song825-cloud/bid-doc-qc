# 投标标书质检（bid-doc-qc）

> 对着招标文件逐条审投标技术标，查出前后矛盾、漏项与错字，输出带 **投标 / 招标双列页码** 的 Word 质检报告与整改清单。

一个 WorkBuddy Skill。把「人工逐条比对招标文件与投标文件」这件反复消耗精力的事，固化成可重复执行的流程。

---

## 解决什么问题

投标截止前审标，常见痛点是：

1. **翻不动**——招标文件几百页、技术标上千页，靠人眼通读时间不够；
2. **找不到**——看出"填筑量前后不一致"，但翻不回去是哪几页，整改时又重找一遍；
3. **写不完**——审出的问题散在纸质笔记，最后拼不成一份能交出去的清单；
4. **重复劳动**——同类问题（如模板残留的项目名误写 8 处）被反复记录，报告臃肿、重点被淹没。

本技能的输出是**一张按问题归并的表**：一个问题一条记录，全部出现页码合并到该行，直接对着页码翻页整改。

## 能力范围

**四重质检**（固定口径）

| 序号 | 维度 | 查什么 |
|---|---|---|
| 第一重 | 资格审查与符合性 | 资质、业绩、人员、承诺函、形式要件是否齐全有效 |
| 第二重 | 评分点响应 | 招标文件评分标准逐条对应，缺项、错位、应答空心化 |
| 第三重 | 逻辑冲突 | 跨章节交叉校验：工期、工程量、设备、标段范围、地名、单位名称 |
| 第四重 | 错字与格式 | 模板残留、错别字、编号断档、单位符号、章节引用错误 |

**三项专项核查**（按需追加）

- **专项 H** 工期与节点前后矛盾（投标文件 vs 招标里程碑表 vs 答疑澄清）
- **专项 E** 设备配备与对应部位功效是否匹配（含"清单里有、正文里没有"）
- **专项 Q** 工程量在投标文件内部的一致性（同一部位多个数值）

## 交付物

默认产出**问题清单版**（8 张表、约 20–25 条问题）：

| 列 | 说明 |
|---|---|
| 编号 | 按等级分组编号 |
| 问题 | 一句话说清错在哪 |
| 等级 | P0 致命 / P1 严重 / P2 一般 |
| 原条目 | 对应完整版报告的条目号，便于回溯取证 |
| 出现位置（投标页码） | 全部出现页码，可直接翻页 |
| 招标依据页码 | 招标文件 / 答疑 / 图纸的出处 |
| 处理建议 | 怎么改 |

另可按需产出**含页码版完整报告**（取证底册，逐条附原文摘录）。

## 安装

三种方式任选：

1. **技能市场**：WorkBuddy 左侧「专家·技能·连接器 → 技能」，搜索「投标标书质检」安装。
2. **本地导入**：下载本仓库 zip，在「添加技能 → 上传技能」中导入。
3. **克隆到技能目录**（便于跟随更新）：

```bash
git clone https://github.com/Song825-cloud/bid-doc-qc.git ~/.workbuddy/skills/bid-doc-qc
```

安装后重启 WorkBuddy，对话中提到「标书质检 / 四重质检 / 审标书」即可触发。

## 运行环境

| 项 | 要求 | 说明 |
|---|---|---|
| 操作系统 | Windows | 页码定位依赖 Word COM 自动化 |
| Microsoft Word | 已安装 | 用于重新分页并取真实页码；无 Word 只能做解析与文本扫描，拿不到双列页码 |
| Python | 3.10+ | `pip install python-docx pywin32 pymupdf` |

`scripts/run.cmd` 会依次探测 `python`、`py -3.12`、`py -3.11`、`py`，用 `import docx` 实测后选中可用解释器；也可用环境变量 `BID_QC_PY` 指定。

## 使用流程

```
0. 环境准备        确认 Windows + Word + Python 依赖
1. 解析投标文件    parse_bid.py  → 结构化文本
2. 逐维度扫描      scan_*.py     → 只标可疑点，不下结论
3. 人工核对取证    回到原文确认，排除误报
4. 页码双列定位    Word COM 取投标页码 + PDF 取招标页码
5. 生成报告        build_slim.py → 问题清单版 docx
6. 回归自检        check_slim.py → 断言全过再交付
```

## 换项目使用

本仓库只提供**方法框架**：`assets/data_rc_EXAMPLE.py` 是虚构示例，不含任何真实项目数据。新项目必须按实际审查结果重建：

| 需要重建 | 内容 |
|---|---|
| `data_rc`（问题清单数据） | 编号 / 问题 / 等级 / 页码成员 / 招标依据 / 建议 |
| `data_s` 系列（明细数据） | 各维度取证结论（完整版报告用） |
| `toc.json` 的 `toc_end` | **先跑 `pages_head.py` 实测**封面与目录页范围，不要凭经验假设 |
| `check_slim.py` 的期望值 | 条数、等级分布、列数断言 |

## 设计取舍

- **为什么默认交问题清单版，而不是逐条批注版**：批注版适合自己看，不适合交给领导或整改执行。清单版一页一条、页码可翻，可直接分工。
- **为什么"一因一记"**：同类问题（如模板残留误写 8 处）合并为一条、页码全并，报告条数从 80+ 降到 20+，重点才浮出来。
- **为什么页码必须实测**：docx 无固定分页，Word 重新排版后页码会漂移；凭 PDF 页码或估算必然错位。
- **为什么扫描脚本只找线索不下结论**：机器判断易误报，结论须由人回到原文确认，脚本只负责缩小范围。

## 已知限制

- docx 无固定分页，调整字体/页边距/插图后页码整体漂移，页码以报告出具时的排版状态为准。
- 图片内文字不做文本核验（图纸、扫描件中的内容需人工确认）。
- 工程量清单若单独成册未提供，清单逐项比对无法完成，会标注为待核验。
- 非 Windows 环境可做解析、扫描、报告生成，但拿不到投标/招标双列页码。
